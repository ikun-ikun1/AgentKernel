# AgentKernel 项目背景说明

## 1. 项目背景

实习阶段我用 Claude Agent SDK 搭了一个配置化的 Agent 工作台（AI Agent Workbench），学会了「用框架」搭平台：Web 对话、Agent 配置化、CLI/MCP 工具接入、人工确认、审计日志。

但框架把 Agent Runtime 的核心机制都封装好了——主循环、工具调用、上下文管理、失败处理，我「会用」却「讲不清底层」。面试官如果问「ReAct 循环怎么实现、工具调用返回非法 JSON 怎么办、上下文太长为什么忘事」，只用过框架的人只能答「框架帮我做了」。

因此，个人项目不是再做一个业务平台，而是选择几个关键问题做研究：先不用 Agent 框架，从零写出可解释的 Runtime 基线，再针对模型输出不稳定、上下文超限和文档更新等问题做改进验证，把实习中的「会用」补成「会实现、会优化、会验证」，形成「会用 → 会理解」的互补主线。

### 1.1 互补关系一览

| 维度 | AI Agent Workbench（实习，会用） | AgentKernel（个人项目，研究与验证） |
|------|-------------------------------|------------------------------|
| 核心问题 | 用 Claude Agent SDK 快速交付团队工作台 | 讲清 Agent 主循环 / 工具调用 / 上下文管理底层 |
| 主循环 | SDK 内置 | 手写 ReAct 循环 |
| 工具接入 | 面向业务的 CLI/MCP Adapter、Agent 白名单 | 最小工具注册表 + JSON Schema 子集校验 + 自实现 MCP client |
| 失败处理 | 依赖框架 | 坏 JSON 分层修复 + 允许清单 + 工具错误回灌 |
| 上下文 | SDK session、跨会话记忆和 Web 会话 | 首条要求保留 + truncate/compact 策略实验 |
| MCP / RAG | 业务 MCP 工具和制度问答、业务上下文编排 | MCP 协议最小实现 + 检索实验样例 |
| 演示形态 | Web 平台（配置化 + 审批 + 审计） | CLI + 单元测试 + eval（可解释、可走读） |

### 1.2 硬边界：不做 Workbench 的第二份实现

Workbench 的目标是交付一个面向用户的业务应用；AgentKernel 的目标是拆解应用底层依赖的 Runtime 机制。两者允许共享概念，但不重复建设同一层产品能力。

| 能力 | Workbench 负责 | AgentKernel 负责的研究实现 |
|------|----------------|------------------------------|
| 用户交互 | Web、SSE、Agent 选择、会话生命周期 | CLI 输入输出 |
| Agent 组织 | manifest、子 Agent、业务 prompt/skills | 单个 Runtime + 固定 system prompt |
| 工具系统 | 业务 CLI/MCP Adapter、审批和权限 | Tool Registry、调用契约、参数校验 |
| 持久化 | 用户会话、跨会话记忆、草稿、审计 | MySQL 会话/文档存储、checksum、chunk 和可选向量索引 |
| 知识库 | 业务制度 RAG、权限和 Agent 上下文注入 | 文档解析、增量索引、混合召回、来源追踪 |
| MCP | 业务工具暴露和接入 | stdio/JSON-RPC 协议实现与测试 |
| 安全 | 企业鉴权、审批、工具隔离、凭据隔离 | allowlist、只读样例、基础输入边界 |

AgentKernel 不做文档管理 UI、业务权限和审批；索引一致性、检索召回和引用保留仅作为研究验证内容，不承诺生产级知识库能力。

## 2. 项目一句话介绍

AgentKernel 是一个用 Python 从零实现的 Agent Runtime 研究原型，不依赖 LangChain / Claude SDK。它通过 CLI、测试和评估脚本验证 ReAct、Tool Calling、上下文管理和 MCP 协议，并用一个检索样例验证文档增量索引、混合检索和来源保留。

## 3. 研究路线：先复现，再优化

1. **复现基线**：参考 agent-study 的 Agent 教学设计，实现 ReAct、工具注册、观察回灌和持久化记忆，先证明理解 Agent 的基本组成。
2. **工程参考**：参考 OpenClaw 对工具调用修复、允许清单和载荷边界的处理思路，不复制其实现，提炼为适合本项目的 Python 版本。
3. **问题驱动优化**：围绕“模型输出不稳定”和“知识库更新不稳定”两个问题，增加分层降级、工具安全边界、checksum 增量更新、MySQL ngram 基线和可选向量回退。
4. **验证方式**：通过 fake LLM、故障输入、文档重复/修改和 MCP 子进程场景验证改进是否有效，而不是只验证成功路径。
5. **面试故事**：实习「会用」框架交付应用，个人项目先复现原理、再针对问题优化，一条线串起来讲。

## 4. 目标与业务场景

个人项目没有「业务用户」，它的「用户」是面试官。核心场景是证明原理级工程能力，典型演示：

1. 多轮对话  
用户连续追问，第 10 轮还记得第 1 轮的要求（上下文不丢）。

2. 工具调用  
用户问「现在几点」「帮我算 123*456」，Agent 调内置工具回答。

3. 知识库问答  
用户问「XX 是什么」，Agent 走 MCP 调知识库，回答带来源引用。

4. 可靠性优化
故意让模型输出非法 JSON，比较直接解析、分层修复和纯文本降级，验证 Agent 不因异常输出崩溃。

## 5. 项目故事（面试逻辑）

面试或复盘时按以下逻辑讲述：

1. **问题是什么**  
Agent 应用开发不能只会套框架。框架封装的 ReAct、工具调用、上下文管理，是 Agent 岗面试的核心考点，只会用框架答不清原理。

2. **我做了什么**  
我用 Python 从零实现了一个可解释的 Agent Runtime，不依赖任何框架：ReAct 主循环、工具调用契约、参数校验、非法 JSON 三层修复、上下文策略和 MCP 协议客户端；另外实现了一个使用 MySQL 持久化、带 checksum 增量更新、全文/向量混合检索和来源元数据的知识库检索样例。

3. **技术上怎么做**  
先实现「思考 → 行动 → 观察 → 回复」的 ReAct 基线；再针对模型输出不稳定增加平衡括号提取、格式修复、工具名允许清单和 payload 上限，失败时降级为普通文本；针对上下文超限保留首条用户要求并对旧消息做摘要压缩，压缩失败再截断；检索样例则用 checksum 增量更新，保留 FTS5 基线并在向量依赖不可用时回退；MCP client 端自实现 `tools/list` + `tools/call`，server 端提供官方 SDK 可选适配和纯 Python stdio 实现。

4. **结果是什么**  
系统能演示「多轮对话 → 调工具 → 知识库带来源 → 坏 JSON 不崩」的闭环，并能通过故障输入和文档变更场景说明优化策略如何降级和恢复。相比直接用框架，它不仅证明我理解底层机制，也证明我能围绕具体问题做工程改进。

5. **还缺什么**  
当前是个人学习和求职用的研究原型，不是 Workbench 的业务产品，也不是生产级 Agent 框架或知识库系统。若用于企业场景，仍需补充组织权限、租户隔离、部署运维、监控告警和针对业务语料的离线评估。

## 6. 项目定位

本项目定位为个人学习 + 求职用的可演示原型。

应该做到：

1. Runtime 主流程能跑通（CLI 多轮 + 工具 + MCP 示例）。
2. 架构边界清楚（Runtime、工具协议、MCP 传输、检索实验与业务应用职责分明）。
3. 错误处理可靠（坏 JSON 不崩、工具报错回灌）。
4. 面试故事完整（原理讲得清）。
5. 参考 OpenClaw 与 RAG 工程实践，理解工业级 Agent/RAG 的设计取舍。

不应该做到：

1. 做成第二个 AI Agent Workbench 或完整商业化 Agent 平台。
2. 接 IM 渠道（飞书等），CLI 演示足够。
3. 追求多租户、插件市场、企业级运维。
4. 做业务知识库 UI、权限和多租户；混合检索、增量索引、引用追踪和离线评估仅作为检索优化实验保留。
5. 追求 LangGraph / Claude Agent SDK 级别的通用平台能力；本项目只实现可解释的 Runtime 基线和针对具体问题的优化。
